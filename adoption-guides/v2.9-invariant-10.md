# Adoption guide — INVARIANT 10 (pre-action fact presentation, v2.9)

**For adopters of KB-Orchestrator-Core ≥ v2.9.** Closes the v2.9 unresolved item from `CHANGELOG.md`. Normative for projects inheriting `agents.config.yaml` from this blueprint.

## What INVARIANT 10 requires

Every state-mutating tool call (`Bash`, `Edit`, `Write`, `MultiEdit`, `NotebookEdit`, delegated dispatch, network POST/PUT/DELETE, MCP write tools) **MUST** be preceded by a user-visible four-fact block:

1. The current request restated in one sentence.
2. What the action verifies or produces.
3. The files the action will read or modify.
4. A verbatim quote of the user/orchestrator directive being acted upon.

Read-only tools (`Read`, `Grep`, `Glob`, `WebFetch`→`sources/`, `WebSearch`) and task-tracker calls are CARVED OUT — no fact block required.

The full normative text lives in `00-overview/invariants.md` INVARIANT 10 and `SYSTEM-BLUEPRINT.md` §2.

## Why this is an architectural property, not a hook preference

INVARIANT 10 is the per-tool-call analogue of INVARIANT 8 (source-saving) and INVARIANT 9 (orchestrator-only writes). Without it, a delegated agent can mutate state — files, commits, ledger rows — without the orchestrator ever seeing the request-to-action chain. That breaks the trust model in §19: the orchestrator can no longer detect reward hacking by inspection because actions and their justifications have been decoupled.

The gate is **inherited** by every project that loads `agents.config.yaml` from this blueprint. Adopters do not opt into the gate; they choose an enforcement mechanism for it.

## Adopter checklist (minimum viable enforcement per runtime)

### Claude Code (the harness this blueprint was developed in)

1. Install the `gateguard` skill (`everything-claude-code:gateguard`). It registers a `PreToolUse` hook that intercepts `Bash`, `Edit`, `Write`, `MultiEdit`, `NotebookEdit` and demands the four-fact block before the call goes through.
2. Verify the hook is wired by attempting any state-mutating tool call without first emitting facts — the call should return a `[Fact-Forcing Gate]` error that quotes the missing facts.
3. Set in `agents.config.yaml`:
   ```yaml
   policy:
     pre_action_fact_presentation_required: true
     pre_action_fact_enforcement_mechanism: gateguard-skill
     on_pre_action_fact_missing: reject
   ```
4. For each adapter you operate, ensure the probe response advertises `enforces_pre_action_facts: true` (in-process gate) or `"orchestrator-side"` (orchestrator emits the block on the adapter's behalf). Adapters reporting `false` may only fulfil read-only roles.

### Claude Agent SDK (custom orchestrator)

1. Register a `PreToolUse` callback on the SDK client that inspects every outgoing `tool_use` block:
   - If `tool.name` is in the `state_mutating_tools` list (defined in `agents.config.yaml`), require the immediately-preceding assistant message to contain the four-fact pattern.
   - Reject the call (do not emit it) when the pattern is missing. Return an error that names the missing fact so the agent can self-correct.
2. Sample matching pattern (regex, multi-line, liberal in formatting, strict on completeness):
   ```
   /1\.\s+(?:Request|User request).*?\n.*?2\.\s+.*?(?:verifies|produces).*?\n.*?3\.\s+(?:Impacted|Files).*?\n.*?4\.\s+(?:Quote|User instruction).*/s
   ```
3. The adapter probe response should report `enforces_pre_action_facts: true`.

### Bridge-only adapters (codex-bridge and similar)

Adapters lacking an in-process callback (the bridge dispatches a job, observes the result, and cannot intercept individual tool calls within the job) MUST report `enforces_pre_action_facts: "orchestrator-side"` in their probe response. The orchestrator emits the four-fact block in the dispatched prompt envelope before each delegation:

```
<pre-action-facts>
1. Request: <one-sentence restatement>
2. Verifies/produces: <effect>
3. Impacted: [<paths>]
4. Quote: "<verbatim directive>"
</pre-action-facts>

<task>
<role-specific instructions...>
</task>
```

The §25 dispatch shim Step 8 SCHEMA gate then verifies the receiving agent's `execution-log.md` shows the fact block present for every state-mutating invocation it logged (per `60-schemas/execution-log.md` "Pre-action fact presentation"). A delegated job that mutated state without surfacing the block fails Step 8 with subtype `inv10-fact-missing` and is re-delegated or escalated per `validation.on_validation_failure`.

### Custom CLI adapters (no callback, no in-process gate)

Wrap the CLI in a host-side script that:

1. Reads the orchestrator-provided pre-action fact block from a known location (env var, file, stdin).
2. Echoes it into the CLI's invocation log before the underlying command runs.
3. Refuses to execute the command if the block is malformed or absent.

A reference wrapper template (`tools/host-shell-wrapper.sh`) is tracked as future work in `CHANGELOG.md` v2.10 unresolved items.

## Validating your adoption

Run, in order:

1. `tools/verify-frontmatter.sh --strict` — confirms the schema_version of `agents.config.yaml` supports the v2.9 policy block.
2. `tools/build-bundle.sh --check` — confirms bundles load the invariants file naming INVARIANT 10.
3. **Smoke test**: dispatch a state-mutating role (e.g. `executor.commercial`) without the orchestrator emitting the fact block. Expected: `rejected-schema` with subtype `inv10-fact-missing` and a re-delegate or escalate per policy. If the dispatch silently succeeds, your enforcement is incomplete.

## Migration path for projects pinned to `config_revision: 1`

Projects loading `agents.config.yaml` with `config_revision: 1` (pre-v2.9) continue to operate. The orchestrator emits a one-time warning at session start recommending the bump. To upgrade:

1. Bump `config_revision: 1 → 2`.
2. Add the four `policy.pre_action_fact_*` knobs from this guide.
3. Annotate every adapter block with `enforces_pre_action_facts` and `pre_action_fact_mechanism`.
4. Install the runtime-specific enforcement mechanism above.
5. Re-run the validation steps.
